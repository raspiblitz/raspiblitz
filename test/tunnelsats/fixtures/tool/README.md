# Tool documents for the contract-call tests

| File | Source |
| :-- | :-- |
| `detect_none.json`, `detect_legacy.json`, `detect_managed.json`, `detect_managed_cln.json` | `generate.sh`: real `detect --json` documents of the pinned `tunnelsats.sh`, produced by its own unprivileged harness (no install; a standard v3 install after #204; a managed install; a managed CLN install with the drop-in of `lightningd.service`, so `managed_ln_dropin` is present). `uname` and `wg --version` are stubbed so no data of the generating machine appears. |
| `install_ok.json`, `install_ok_stopped.json` | hand-written with the field list of `cmd_install_managed` at the pinned commit (`managed`, `profile`, `impl`, `unit`, `node_user`, `uid_backstop`, `iface`, `slice`, `tunnel_started`, `ln_was_active`, `ln_restarted`, `node_config`, `other_ln_units`); the unit carries the start guard exactly in the form of `lnd.install.sh`, so `node_config` is `clean` |
| `install_capability.json`, `install_managed_present.json` | hand-written failure documents (`ts_fail` envelope) for exit 6 (`E_CAPABILITY_MISSING`) and exit 7 (`E_MANAGED_PRESENT`), with the code, class and message of `cmd_install_managed` |
| `uninstall_clean.json`, `uninstall_disabled.json`, `uninstall_incomplete.json`, `uninstall_not_installed.json` | hand-written with the field list of `cmd_uninstall_managed` at the pinned commit (`managed`, `unit`, `remaining`, `ln_was_active`, `ln_started`, `ln_disabled`, `node_config`, `action_required`, `announce_cleanup`, `warnings`). The tool reads the start-guard variable in `ExecStart` through when the unit carries the guard in the expected form; REMOVE deletes the guard's env file first, so a Tor-only `lnd.conf` is `clean`: the tool starts LND again and takes the former VPN address out of its node announcement (`uninstall_clean.json`). With TunnelSats settings in `lnd.conf` it keeps LND stopped and disables the unit (`uninstall_disabled.json`); an incomplete removal starts nothing (`uninstall_incomplete.json`). |
